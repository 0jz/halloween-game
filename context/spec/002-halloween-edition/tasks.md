# Tasks: Halloween Edition

Six slices: five that each add something a player can see, then Feature Testing & Regression. Slices 1 to 3 are the night (everything cosmetic), slice 4 adds ducking and bats, slice 5 adds the hat, candies and hearts. The game stays runnable with `npm run dev` after every slice, and `npm test` must be green at the end of every slice. Each implementation task includes its own unit tests, proven RED first (CLAUDE.md). While iterating, run only the single test file of the task; run the full `npm test` at the end of a slice. Verify tasks use `npm test` plus a short look at `npm run dev` or a throwaway Playwright script against `npm run preview`.

**Cut lines.** Tier 1 is complete after slice 3, Tier 2 after slice 4, Tier 3 after slice 5. Commit and push after each slice (`ex7: slice N`).

## Parallelization Plan

Every slice funnels through `src/game.ts`, `src/types.ts`, `src/tuning.ts`, `src/render.ts` or `src/main.ts`, so slices and most tasks run one at a time in document order. Two waves are safe because their tasks write different files.

| Wave | Tasks in parallel | Files each task owns | Starts after | Followed by |
|---|---|---|---|---|
| 4.A | 4.2, 4.3 | 4.2: `src/input.ts`, `src/input-dom.ts`, `tests/input.test.ts`, `tests/input-dom.test.ts` · 4.3: `src/sprites.ts`, `tests/sprites.test.ts` | task 4.1 | join, then 4.4 |
| 5.A | 5.2, 5.3 | 5.2: `src/pickups.ts`, `tests/pickups.test.ts` · 5.3: `src/sprites.ts`, `tests/sprites.test.ts` | task 5.1 | join, then 5.4 |

Rules for a parallel wave (every task in a wave gets these in its prompt):

1. A task writes only the files listed for it in the table; shared files (`src/types.ts`, `src/tuning.ts`, `src/game.ts`, `src/render.ts`, `src/main.ts`, `tests/helpers.ts`, `tasks.md`) are never written by a parallel task. If a task finds it needs a change in a file it does not own, it stops and reports instead of making it.
2. A task's tests import only its own module plus `types.ts`, `tuning.ts` and modules finished in earlier waves or slices, never a module its sibling is still writing.
3. While the wave runs, a task runs only its own test files (`npx vitest run tests/<its-file>.test.ts`) and lints and formats only its own files (`npx eslint <files>`, `npx prettier --check --end-of-line auto <files>`). It does **not** run `npm test`, `tsc` or the whole suite, because the sibling's half-written file would break it.
4. RED validation reverts only the task's own files, from a backup copy it made first (copy the file, revert, run, restore from the copy). Never `git stash` without a path list, `git checkout .`, `git reset`, `git clean` or `prettier --write` on a path the task does not own; those would also wipe the sibling's work. No commits by a task.
5. No task adds or upgrades a dependency, starts a dev server, or runs the e2e test.
6. **Join.** When both tasks of a wave are done, and before anything after it starts, the orchestrator reads both reports, spot-checks one file of each, and runs `npm run typecheck && npm test` once. If it fails, the task that owns the failing file is reopened (`[x]` back to `[ ]`) and fixed alone before anything proceeds.
7. **How to launch.** The orchestrator starts the two tasks of a wave as separate subagents in a single message, waits for both reports, then marks both `[x]` and runs the join. Everything outside a wave runs one task at a time in document order.
